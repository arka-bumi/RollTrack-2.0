# ARCH_260926 — Technical Architecture & Data Specification (RollTrack)
*Dokumen mesin final 26-09-2026. Selaras `PRD_260926.md`. Menggantikan `Data Flow_Architecture General.md`.*

## 1. Keputusan Terkunci
1. **Middleware tipis (Node.js + MongoDB)** + snapshot pattern per merek (`malilkids` | `anakkecilku`).
2. **Dua spreadsheet inventory** (MALILKIDS / ANAKKECILKU), master + histori per file.
3. **Kode Produksi `{M|A}{DDMMYY}-{SKU_PRODUK}-{NN manual}`** — `M` = Malilkids, `A` = Anakkecilku; NN diisi staff; middleware validasi format + dedup unik (merek, hari, SKU, NN) → `409` bila duplikat.
4. **Tanpa ruangan, tanpa harga/IDR, tanpa sinyal PO, tanpa blokir stok negatif.**
5. **Dashboard baca operasional real-time**; tab Summary Sheets = pembanding audit (hasil akhir konvergen; beda hanya latensi/offline/konflik).
6. **Dua tombol sync** (nama dikunci): **Sinkron Database** (master + 2 tab summary, ringan) dan **Sinkron Penuh** (tab History 22rb baris, berat, jarang). Sheets menang saat selisih.
7. **Varian = size** (S/M/L/XL); satu produk + varian beda = SKU beda. Kolom Produk mengandung motif; Jenis hanya nama induk. `relasi_kain` tidak dipakai untuk display roll.
8. **Meter diutamakan**; konversi Kg→meter hanya bila meter kosong, memakai `rasio_konversi_meter` (F. Database Kain kol 12). Sisa berjalan selalu meter (`fabric_rolls.sisa_meter`); tanpa field/display sisa Kg. `tim_cutting` = nama orang dari sesi login.
9. **Mapper mengacu ke `Technical_Pencocokan Kolom Data.xlsx`.** History Penggunaan Kain = 25 kolom (Status Penggunaan Kain di kol 18, Tim Cutting kol 9, Stok Awal kol 10 statis dari History Datang, Jumlah Dibawa Meter kol 11); F. Database Produk: varian kol 2, sku_produk kol 3, status kol 5, sku_kain relasi kol 12. Kolom O (Stok Last Update) dan Selisih selalu dikirim kosong — dihitung rumus sheet, jangan ditimpa.
10. **Detail sync yang mengikat:** angka meter dibulatkan 2 desimal; baris sync tanpa SKU/nama dibuang; status produk kosong → `Active`; baca sheet mulai baris 2 (header dilewati); masters diurut `no_index`, gudang alfabetis.

## 2. Pipeline Data

```text
[ Sheets MALILKIDS ]                       [ Sheets ANAKKECILKU ]
 master + histori Malilkids                 master + histori Anakkecilku
        │                                            │
        ▼ Sinkron Database (ringan)                  ▼ Sinkron Database (ringan)
[ MongoDB brand=malilkids ]                [ MongoDB brand=anakkecilku ]
        │                                            │
        └──────────────────┬─────────────────────────┘
                           ▼
                [ Middleware Node.js (tipis) ]
                 validasi role + merek + kode produksi,
                 tulis operasional, append batch per merek
                           │
        ┌──────────────────┼───────────────────┐
        ▼                  ▼                   ▼
[ HP real-time ]   [ Antrean offline FIFO ]  [ Sinkron Penuh (berat) ]
```

## 3. Skema MongoDB (ringkas — detail field di Excel mapping)
- `fabric_masters` (+`brand`, unique brand+sku; kolom finansial tidak disync; `rasio_konversi_meter` dipakai untuk konversi Kg→meter saat meter kosong).
- `fabric_products` (+`brand`, unique brand+sku_produk; `varian`, `kepala_sku_produk`, `status_aktif_produk` nilai asli sheet; `relasi_kain[]` per kain_ke berisi konversi_1/2 + sku_kain; serve hanya `Active`, dedup per SKU untuk dropdown).
- `fabric_rolls` (+`brand`, unique brand+roll_id, `sisa_meter`, status `1 Roll/Sisa/Habis`, gudang saja; simpan juga `ukuran_asal` + `satuan_asal` dari History Datang untuk cetak QR).
- `usage_logs` (+`brand`; unique brand+`kode_produksi` **hanya untuk kode yang tidak kosong** — transaksi non-produksi mengosongkan kode; `tim_cutting` = nama orang dari token; `stok_awal_meter` = ukuran awal roll saat datang, **statis dari History Datang Kain**; `jumlah_dibawa_meter/kg` input staff; `sisa_stok_setelah_dibawa_meter` = sisa setelah potong ini; `stok_last_update_meter` **tidak dikirim aplikasi** (kolom O dikosongkan saat append) — dihitung sheet via `VLOOKUP` Roll ID ke Summary By Code, selalu nilai terakhir; kolom sesuai History Penggunaan Kain 25 kolom).
- `location_logs` (+`brand`; **tanpa ruangan**; satu baris per roll, sehingga pindah bulk menghasilkan banyak baris).
- `warehouses` (**Master Gudang**) — daftar gudang; isinya identik di kedua merek, jadi **tanpa `brand`** dan dipakai lintas merek oleh Pindah Gudang.

## 4. Endpoint
- `GET /api/v1/masters?brand=` · `GET /api/v1/products/active?brand=` (read-only HP).
- `GET /api/v1/rolls?gudang=` — daftar roll dalam satu gudang (Pindah Gudang, lintas merek; `brand` tidak dipakai, gudang bersama).
- `GET /api/v1/rolls/scan?payload=` · `POST /api/v1/rolls/transfer` (body: `rolls[]`, `tujuan_gudang`, `tanggal_pindah` opsional default hari ini; tanpa ruangan) — `brand` **diturunkan server dari tiap roll**.
- `POST /api/v1/rolls/cut` (body: `brand`, `kode_produksi` terkunci, `produk`, `sku_produk`, `jumlah_dibawa_meter/kg`, `sisa_kain_waste`, `kain_reject`, `status_penggunaan_kain`; `tim_cutting` + `brand` log dari server/token, bukan body) — `brand` dari toggle Cutting. Satu transaksi boleh N roll → N `usage_logs` satu Kode Produksi.
- `GET /api/v1/reports/summary-by-roll-id?brand=` · `GET /api/v1/reports/summary-by-sku?brand=` (baca operasional).
- `GET /api/v1/reports/rolls-by-sku?brand=` — **group-by kolom SKU** dari baris Summary By Roll ID (tab `By Code`) — serve list roll per SKU ke 4.1, tanpa baca tambahan.
- `GET/POST /api/v1/users` · `PUT /api/v1/users/{id}` · `DELETE /api/v1/users/{id}` (kelola operator oleh Admin/Super Admin; kelola admin hanya Super Admin — sesuai AUTH §4, tanpa endpoint `/admins` terpisah). Hapus user hanya mencabut login; log/history tetap.
- `POST /api/v1/sync/database` (Admin/Super Admin): pull master + 2 tab summary per merek, kolom sempit.
- `POST /api/v1/sync/full` (Admin/Super Admin, luar jam sibuk): tarik full History ±1.000 baris/batch untuk rekonsiliasi, Sheets menang. Murni pull — tidak mendorong data harian dan tidak menyentuh antrean (itu jalur selalu-tersinkron).
- `POST /api/v1/stock-opname` — Stock Opname; UI masih terkunci di DESIGN §2 (5.2), endpoint disiapkan sesuai PRD §3.7.
- `GET/PUT /api/v1/sheets-connection` (Super Admin): daftar Spreadsheet ID per merek + hasil **Uji Koneksi** (status baca/tulis per merek). Lihat §6.

## 4.1 Sumber `brand` per konteks
| Konteks | Sumber `brand` | Header `X-Brand` |
| :--- | :--- | :--- |
| Cutting (3.1, 3.5) | toggle staff (Malilkids / Anakkecilku) | wajib |
| Dashboard Kain (4.1–4.5) | toggle staff per layar | wajib |
| Pindah Gudang (2.1–2.4) | **diturunkan dari roll** — tanpa toggle | tidak wajib |
| Scan | diturunkan dari roll | tidak wajib |
| Sync | dipilih admin | wajib |

**Roll ID unik global** dengan format `{YYMMDD}-{Jenis} {Motif} ({Supplier})-{No}({Ukuran})`, mis. `260925-Rayon TTMD Hitam (Idola)-01(25.7)` (= 25 Sep 2026; angka kurung = ukuran saat datang, satuan ikut kolom Satuan). Kedua file Sheets terpisah → `roll_id` selalu memetakan ke tepat satu `brand`; tidak adaambiguitas saat scan/pindah, tidak perlu daftar kandidat.

## 5. Pemetaan Sheets (per merek)
`fabric_masters`→F. Database Kain · `fabric_products`→F. Database Produk (filter Active) · `fabric_rolls`→History Datang Kain · `usage_logs`→History Penggunaan Kain (append inkremental) · `location_logs`→Pindah Gudang (append, tanpa ruangan) · `warehouses`→**Master Gudang** (identik per merek, tanpa brand) · (baca saja) Summary By Code → **Summary By Roll ID** / Summary By SKU.
**Pengecualian:** tab `Pengumuman` hanya ada di file **Malilkids** (tanpa brand; A2 = isi, B2 = atribusi, satu baris aktif) → koleksi `announcements` (replace tiap Sinkron Database) → `GET /api/v1/announcement` (semua role login); mobile menyimpan terakhir diterima untuk fallback offline.

## 6. Catatan Instalasi & Deploy (target: Vercel gratis + MongoDB Atlas + APK internal)

Keputusan hosting (user): backend di **Vercel paket gratis** (serverless), database **MongoDB Atlas** (Vercel butuh DB ter-host), API diakses HP via **URL publik HTTPS**, aplikasi disebar sebagai **APK internal** (tanpa Play Store).

1. **Service account (sekali, manual).** Buat 1 service account di Google Cloud, unduh JSON key, tempel isinya ke env `GOOGLE_SA_JSON` (Vercel env) saat setup — lalu disimpan terenkripsi AES-256 di MongoDB. **Tanpa file lokal** (filesystem Vercel ephemeral; tidak ada `sa.json`). Kredensial ini **tidak pernah** dikirim lewat aplikasi.
2. **Entry serverless.** Backend diekspos via entry serverless + `vercel.json` (bukan `app.listen` biasa). Perhatikan batas timeout paket gratis — Sinkron Penuh sudah dipecah batch ±1.000 baris (§4).
2. **Berikan akses Editor** ke email service account tersebut pada **kedua** spreadsheet (Share → paste email SA → Editor). Nama tab **tidak** dikonfigurasi lewat aplikasi — taken dari §5 dan divalidasi otomatis.
3. **Spreadsheet ID** diambil dari URL `https://docs.google.com/spreadsheets/d/<ID>/edit`. Dua ID ini diinput Super Admin lewat halaman **Koneksi Spreadsheet** (terpisah, khusus Super Admin), lalu diuji tombol **Uji Koneksi** (status baca/tulis per merek).
4. **PIN super admin pertama**: dari env `SUPERADMIN_PIN`, default `000000` bila env kosong. **Wajib diganti** Super Admin lewat Akses dan Sinkronisasi (di atas daftar Admin).
5. **Login wajib online** (verifikasi PIN di server). Cache HP: ±1.000 roll + log 3 hari; sisanya butuh online.
6. Antrean offline dikirim tanpa koreksi; transaksi yang ditolak server **hilang** dari perangkat (PRD §6.1).
7. Kalau hanya satu file spreadsheet yang bisa diakses, halaman Koneksi harus menandai merek itu "belum terhubung" — jangan sampai gagal diam-diam saat sinkron.
